# Android

How Dens runs on Android phones. [design.md](design.md) has what every form shares.

An Android app joins dens from a phone. It hosts none, shares no screen, picks no speaker and has no push to talk. M12 to M14 build it. A spike on Android's emulator, a Galaxy S24 Ultra and a Pixel 9 Pro, all on Android 17, tried the design first, and what it found is below.

- *Shape.* The release's Go binary, built for Android, rides in the APK as `lib/arm64-v8a/libdens.so` and runs as a child process from the app's native library directory, where Android lets apps execute files; Syncthing-Fork does the same, targeting Android 17. A copy elsewhere in the app's files won't run. The page runs in a WebView. A thin Kotlin shell does what only Kotlin can on Android: the foreground service and its notification, the Keystore, permissions, the file picker, downloads (named from their `Content-Disposition`, since the service sends every one as `application/octet-stream`), notifications and audio routing. It talks to the service over the control socket, as `dens open` does, holding one stream as the shortcut helper does.
- *The WebView stays the page's.* The page gets no JavaScript bridge, so nothing in it reaches the shell, and the shell keeps the WebView on the page: every other address, a message's links and YouTube's own included, opens in the phone's browser.
- *The build* uses cgo and the NDK, for Android alone, so name lookups go through Android's resolver and honour its Private DNS; a pure-Go binary finds no resolver there. Pion's interface listing needs `-checklinkname=0` on Android. Android's seams join `internal/platform/host` as `_android.go` files, with `!android` on their Linux counterparts, since Go builds Linux files for Android too.
- *What Android changes.* Apps may lock only 64 KiB of memory since Android 14, 16 pages at 4 KB and 4 at 16 KB, so locked memory falls back to ordinary memory there, which Android swaps only to compressed RAM; Samsung allows 64 MiB. Android kills child processes past 32 across the device, so media jobs run at most two at a time, under the foreground service. Android's seccomp filter kills `rseq` and `io_uring_setup`, which Go doesn't make, and Android 12's also kills `faccessat2`, `openat2`, `close_range`, `clone3` and `epoll_pwait2`, which Go's standard library avoids there; code that calls them directly gets the process killed. Apps that target Android 17 ask for `ACCESS_LOCAL_NETWORK` to reach their own subnet, which the phone's Wi-Fi is; loopback, the control socket and addresses beyond the router don't need it, so the app asks only for a den that resolves to one on the phone's subnet. The shell sets `TZ`, which Go reads for its local zone, and `TMPDIR`.
- *A phone sleeps.* Go's timers run on `CLOCK_MONOTONIC`, which stops while the CPU is suspended, and a phone off screen suspends between packets, 95% of the time on a desk. So nothing waits on a timer for a time on the wall clock: the session's renewal checks the wall clock each time the den's ping wakes the phone, as a timer set for ten minutes before the hour fires hours late there. And a dropped connection, after which no ping comes to wake the phone, asks the shell to hold it awake while it reconnects, with an alarm behind that. Durations in the logs come from the wall clock.
- *What the page loses.* Android's WebView has no `getDisplayMedia`, so the page hides sharing, while watching others' shares works; no usable `setSinkId`, so the shell routes audio; no notifications, so the service decides what to notify and the shell posts it; and no Clipboard API, refused even after a tap, so the page copies through `document.execCommand('copy')`. Android 12's own WebView, 91, doesn't know the CSP's `'wasm-unsafe-eval'`, which RNNoise needs, so the app checks the WebView's version against a floor and asks for an update below it.
- *Calls.* Chromium freezes a hidden page a minute after its sound stops, which suspends its audio contexts and pauses its audio elements: a call stops sending, and stays silent once the page thaws. So while the page has the microphone, the shell tells the WebView its window shows, whatever the screen does, and the page plays its audio elements again whenever it thaws from a freeze. Android fixes a stream's use as Chromium opens it: an audio context made once the microphone is open plays as a call's, and one made before it as media, under the media volume and never on a Bluetooth headset during a call. The members' voices, played through audio elements, played as media too. So the page plays a call through an audio context it makes once the microphone is open, which a WebView lets start without a tap, and the call then follows the route the shell sets with `setCommunicationDevice`: the loudspeaker to start with, the earpiece, or a Bluetooth headset.
- *Keys.* The data key is wrapped with a Keystore key, hardware-backed where the phone has the hardware, whose material never enters the app: in StrongBox on both phones the spike tried, unwrapping in 34 to 50 ms, and with the phone locked too. The shell unwraps the data key at start and hands it to the child over a pipe. Android's Auto Backup leaves Dens's data out, since the Keystore key can't go with it: moving phones is a Dens backup and restore, as between computers.
- *Staying connected.* A foreground service holds the den connections while the app isn't on screen, with the notification that comes with it, as Google-free messengers do, and takes the microphone's type too while the page has the microphone. It kept a den's socket through a night of Doze, and on a sleeping phone the den's ping every 30 s, about 140 wakes an hour, costs about 1% of the battery a night. Swiped from recents, the app runs on; killed, the service starts again. Battery set to Restricted cuts the app's network as soon as it leaves the screen, and Android stops its service soon after, while Samsung's deep sleep kills the app outright. So the app says so when Android reports it restricted, and the install guide asks Galaxy owners to put Dens among Never auto sleeping apps, since Samsung puts unused apps to sleep by default. Later, a den could wake its members' phones through UnifiedPush, an additive protocol change that needs nothing from Google.
- *Distribution.* The APK on the release host, with an updater in the app that downloads each update and hands it to Android's installer, where the member taps to install it, and that steps aside when F-Droid installed it; and Dens's own F-Droid repository, from which F-Droid 2.0 updates apps automatically. Android 12 and later let an app update itself without a prompt, but Play Protect calls an app that asks for that, through `UPDATE_PACKAGES_WITHOUT_USER_ACTION`, harmful, and passes one with `REQUEST_INSTALL_PACKAGES` alone. Play Protect's verdict sticks to a package and its key, so development builds use a package name and key of their own. Installing from the browser, Android warns that the file might be harmful, asks to let the browser install apps, and offers Play Protect's scan. Not Google Play for now: its rules for new developers, its declarations for foreground services and its ban on apps updating themselves cost more than its reach is worth to Dens yet. Samsung's Auto Blocker, on by default on Galaxy phones that shipped with One UI 6.1.1 or later, blocks both until the member turns it off, so the install guide says how.
- *Signing.* Every update must carry the APK's signature, so its key can't be replaced if lost: it lives in CI, encrypted, and offline in two places. Android 17's hybrid signature (scheme v3.2, a classical key with ML-DSA) counts as a rotation from it, so it can be added later.
- *Google's developer verification.* Dens doesn't register. Once Google's verification covers apps installed outside its participating stores, as it has in Brazil, Indonesia, Singapore and Thailand since September 30, 2026, and plans everywhere in 2027, a certified phone installs an app from a developer it hasn't verified only through its "advanced flow", set up once per phone: Developer options, a day's wait, then on for 7 days or for good. ADB still installs anything. While the flow is off, updates to such an app fail, so the install guide says to choose for good, and the updater, when the system refuses an update as unverified, says how to turn the flow back on. Phones without Google's certification, such as those running GrapheneOS or LineageOS, check nothing, and the guide says so. Registering would make the app's ordinary install depend on Google's registry, which Google can withdraw from an app country by country, where the design has nothing depend on a company staying friendly; and it can't be taken back, since Google keeps the identity it was given. Not registering can be: when two signing keys claim a package name, Google gives it to the key with more than half its installs.
