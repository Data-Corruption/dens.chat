# Working on a step

How a milestone's step goes, from its branch to its merge. The plan is [milestones.md](milestones.md)'s, and running the harnesses is [testing.md](testing.md)'s.

## The plan

A milestone's plan is written in milestones.md and reviewed before anything is built: its row in the table, its steps, and a testing section naming each step's checks, stating the options and the pick, with a reason each. A design question that needs evidence first gets a spike in `spikes/`. The plan commits first on the first step's branch and rides its pull request, unless something is built before the first step, as a check the steps rely on, when it takes a pull request of its own.

## A step

1. **The branch.** Cut it from an up-to-date main, short and kebab-case, named for the step (`cleanup-notes`). Read AGENTS.md, the step and what the testing section names for it, and the design parts it touches.
2. **The build.** A pick of the plan's that proves wrong is raised before the course changes. A step that departs from its plan says how in its step in milestones.md, for the wrap-up to fold into the design.
3. **The checks.** Run what the testing section names, `-lint`, `-js` after touching the page's scripts, `-docs` after the site, and each harness whose script changed, one heavy suite at a time; run the Go race suite when Go outside `internal/ui` changed, and `go test -race ./internal/ui/...` for changes to the page alone. Browser checks run in Chromium and Firefox. A change to a screen's words, layout or selectors can break the checks that use them, named in the step or not: search `scripts/test/browser/` and `scripts/test/android/` for what changed, update any affected drivers, and run each matching browser check (`phone` among them for 390px layout changes). Run `-android-e2e` locally only when `android/`, Android's host seams (`*_android.go`), or Android-specific WebView/shell behavior changed, when the step's testing section specifically asks for it, or once at a milestone's end. The manual test waits for the milestone's end.
4. **Stop, or commit.** Stop before committing, the tree left uncommitted with a proposed split and the pull request's text, when something strange comes up, when a decision the plan doesn't settle arises, or on a milestone's last step, whose manual test comes first. Otherwise commit by layer, in this order: Go (the den, the client, the service); the page; the Android shell; the checks; the docs; on a milestone's last step, the wrap-up, which folds the plan into the design docs and keeps its row; and `Release vX.Y.Z`, which dates the CHANGELOG's heading. Each commit that changes Go passes the race suite and `-lint` alone, checked in a scratch worktree at that commit. With no interactive staging, a file's changes split across commits by writing the first part with `git hash-object -w` and staging it with `git update-index --cacheinfo`.
5. **The pull request.** Push the branch and open the pull request into main with `gh pr create`. Its text is for the reviewer: a paragraph on what it does and whether merging publishes a release, what to look at, the picks beyond the plan, what was checked, with counts, and what's deliberately left out. Only a pull request into main runs CI, so a stack of them goes in one at a time.
6. **CI.** A pull request runs the jobs `ci.sh --plan-pr` picks from the files it changes ([release.md](release.md#ci-jobs)). Read a failure from its job's log, `gh run view RUN --log-failed`, and an e2e's logs from the run's artifacts, `gh run download RUN -n den-e2e-logs` ([testing.md](testing.md#cis-logs)). A test that fails there and not here usually loses a race to a slower runner ([testing.md](testing.md#the-race-suite)).
7. **The merge.** It merges with a merge commit, which keeps the layers. Then the branch goes, on GitHub and here, `git fetch --prune` drops the remote's, main is synced, and the next step's branch is cut from it. A fix found after a merge takes a branch and a pull request of its own, as does one for main's release run, which [release.md](release.md#retry-an-interrupted-release) says how to resume.

## The milestone's end

- **The manual test** runs once, at the milestone's end, in Chromium, Firefox and the Android app on a phone. Its steps are a numbered list grouped by area, of only what needs hands.
- **Its builds** come from `scripts/dev/stage.sh VERSION DEST`: this tree's release builds, the page in them, and the Android app's development APK, at a prerelease of the coming version, which sorts before the release, so the release updates over it once published. Staged again after a fix, at a prerelease that sorts after the last, they're what `dens update --skip-verify` finds on the test machines, which leave them through the guide's installer once the release is out.
- **What a staged build did is done.** A migration step a staged build ran on a machine whose data matters is frozen as a released one is: a schema change after it is a step of its own. A fix to the media module reaches what members play once the den runs it, since the den strips each file again, so it's tried against a den on the new build.
- **The release.** The last step's pull request carries the dated CHANGELOG heading, and its merge publishes. A guide page on a feature lands with it, since the site deploys from main at once. Then check the release as [release.md](release.md#publish) lists.
