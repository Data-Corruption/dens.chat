# Dens — Milestones

What each milestone built, the plan for the one under way, and ideas for after it. The design they build toward is [design.md](design.md), with each deployment form's in [installed.md](installed.md), [flatpak.md](flatpak.md) and [android.md](android.md): a section named here, such as Global shortcuts, is one of theirs unless it's one of this file's.

A milestone's plan is written here first, and reviewed before anything is built. Once the milestone is done, what its plan still teaches, such as spike findings and measurements, moves into the design docs' sections, and the rest goes; Git keeps it.

Each milestone ends usable on its own and is tested on Linux and Windows with all four target browsers. All platform-specific code lands in M0, while the seams are still cheap to change; later milestones are shared code, but for M7's keys and the helper's start at login, M9's Flatpak and M11's Android app.

**Why a backup doesn't move a den.** A den lives in the data of the install that hosts it, beside that install's client: its accounts in every den it joined, with their device keys and DM seals, the DM seal new dens start with, and its settings. A backup carries all of it, so a server restored from one is signed in to every den as the same devices as the owner's computer: online around the clock, and signing that device out from either signs out both. And the install the den left keeps its copy, which its client reaches on loopback whether hosting is on or off (`Manager.apiFor`, through `App.OwnDen`), so it never follows the den; nothing short of an uninstall, or a restore over it, deletes that copy. A move takes the den alone, and the install it left then lets its copy go.

M10.1:

- *A cut-off archive is a failure.* A body on the control endpoint ends with a marker, and the client fails without it, so `dens backup`, and the export after it, never keep a file the stream cut short. Today `CallBody` takes the connection closing for the end, so the command keeps what arrived and says the backup was written; a probe that failed a body partway, and one that let the write deadline pass, both got no error and part of the body. The page's download aborts its connection when the archive fails partway, so the browser marks the download failed; today the handler returns, and net/http ends the response as if it were complete.
- *A limit on stalls, not on time.* The control endpoint's 30 minutes for a whole reply (`service.go`) becomes a limit on each write, as the client's reads already have, so a long archive streams to the end and a stalled reader still times out. The command waits up to an hour for the database's snapshot, rather than the 30 seconds it gives any reply.
- *gzip's fastest level.* Uploads are sealed, so they don't compress, and gzip's default level takes them at 116 MiB/s with Go 1.26.7, which releases build with: 200 GB takes half an hour of one core on a Ryzen 7 9800X3D, and longer on most machines. Its fastest level takes them at 950 MiB/s. The format stays the same, so every release restores the archive.
- *Restore checks first.* The archive's database comes before its uploads, so restore checks the app, the schema, the password and the data key as soon as the database is out, before any upload. Today it extracts every file first, so a mistyped password shows only after all of them.
- *Space in place of caps.* Restore's caps, 256 GiB and a million files (`backup.DefaultLimits`), go: an owner can let a den hold far more, and each upload with a preview is two files. Restore refuses at the start an archive larger than the free space, and stops before the disk would fill, saying how much more room it needs, keeping a gigabyte free as uploads do. `dens backup` learns the archive's size before it streams, and refuses when the folder it writes to hasn't room; the page's Back up says how large the file will be.
- *Docs.* Backups and moving says how much room a backup and its restore take: the den's size where the file goes, and as much free, with a gigabyte to spare, on the disk Dens restores it to.

M10.2:

- *The export.* `dens den export` writes a backup archive, in the backup's format, whose database holds the den and none of the client. Its snapshot keeps the vault's check value and the data key sealed under the local password, every `den` table and the uploads; it loses the joined dens, with each account's device key and DM seal, the paired browsers and the vault's DM seal, and its settings start as a new install's. Those rows go with `secure_delete` on, and the snapshot is vacuumed before it's archived, so no free page keeps them. A new field in the manifest says it's a den's export. It takes the local password, and refuses while hosting is on, saying how to turn it off, so nothing reaches the den after its snapshot.
- *Moving from the page.* Once the den exists, Hosting, in the settings' System tab, gains Move the den to another computer. Its dialog says that members can't reach the den until the other computer hosts it, and that the file holds the den but none of the member's own accounts; after the local password, it turns hosting off and downloads the export through the backup's one-time link. Hosting then shows when the den was exported, the guide's i and Remove from this computer, and the den's row on home says it was exported and leads there, rather than to the switch.
- *Exported, and not since.* An export is recorded in the configuration (`DenExported`, when). Turning hosting on again clears it, after a confirmation that another computer may host the den by now, and members would then reach whichever one its address points at.
- *Restoring it* is `dens restore`, as for any backup: hosting starts off, no browser is paired, and the den starts a new sync epoch. Its plan names the den's export, and its last line gives `dens den hosting on` in place of `dens open`. The Flatpak refuses one, since it hosts no den. Home's Finish setting up shows only while the den has no owner, which the dens view now says, so a server holding an export never offers it.
- *Removing the den from the computer it left.* `dens den remove`, and Hosting's Remove from this computer, delete this install's copy once three things hold: hosting is off; the den was exported, and hosting hasn't been on since; and the den answers at its address from this computer and proves its identity there, as the Test beside its address in Manage does (`Manager.CheckAddress`), which with hosting off here means another computer serves it. A failure names the one that didn't hold, and for the address what to try: the other computer hosting behind Caddy, the name pointing at it and the router forwarding there, or, for a router that can't reach its own public address, a hosts entry with the server's local one. Then, after the local password, one transaction deletes every `den` table's rows, with `secure_delete` on; the uploads go; and the den forgets its identity and key in memory, so `OwnDen` reports none. The client's connection to the den starts again at its address, as any den's would, keeping the account there, owner or not, without a restart. The record of the export goes too.
- *Hosting from the command line.* `dens den hosting on`, with the local password, does what the switch does, and prints what it serves: the den's address, the port Caddy forwards to and the media ports; or the port that's held and the installer flag that moves it. `dens den hosting off` asks to confirm that members can't reach the den until it's back on, which `--yes` skips. Both go over the control endpoint, as `dens den owner-invite` does; `dens status` already shows the switch and why a den isn't serving.
- *Docs.* A new guide, Host on a server, after Host a den: a Linux machine that stays on, installed over SSH from an ordinary account, or with `--user` where there's only root, and in a Proxmox or Incus container, Debian 13 with nesting on; moving a den there, from its export to removing the old copy and stopping the old Caddy; reaching it from home, where a router may not reach its own public address; and updates and backups on the server. Backups and moving hands a den on with its export, and loses the warning about whole backups; Host a den points to the new guide. design.md's Backup, restore, move and Handing the den on, and installed.md's hosting and restore, describe the export, removal and the commands.

M10.3:

- *The local password.* `dens password` sets one where there's none, as the page does at the first pairing, or changes it given the current one, which re-wraps the data key only. It's rate limited as the page's checks are.
- *Creating the den.* `dens den create NAME ADDRESS`, with hosting on and the local password, creates the den with no account on this computer, and prints a one-time owner invite that lasts an hour, as `dens den owner-invite` does, which makes another if it lapses. Whoever pastes it into Add a den becomes the owner. Create your den, on the page, stays as it is.
- *The installer's last lines* name the server guide beside `dens open`, where the desktop user has no desktop session.
- *Docs.* The server guide's other start: a den created on the server, its owner invite redeemed from the owner's own computer.

**M10 testing.**

- Go tests:
  - Backups (M10.1): a body cut off partway, by an error or a stalled write, fails `CallBody`, and `dens backup` leaves no file; the page's download of an archive that fails partway ends without the response's last chunk; a reply that streams past the old limit, scaled down, finishes; restore refuses a wrong password before it extracts any upload, refuses an archive larger than the free space, and stops before the disk fills, with the free space faked; and an archive written at the fastest level restores, as does one v1.2.0 wrote at the default level.
  - The export: refused while hosting is on and without the local password; its database has no joined dens, paired browsers or vault DM seal, and a new install's settings, while every den table and upload matches the instance's; it's recorded, and turning hosting on clears the record.
  - A move, with two instances in one test: the one restored from the other's export serves the den once hosting is on, offers no Finish setting up and connects to nothing; the other, once it removes its copy, reaches the den at its address as the owner, with its history and DMs, without a restart.
  - Removing: refused while hosting is on, with no export or with hosting on since, while the address doesn't answer or answers with another identity, and without the local password; otherwise every `den` table and the uploads directory are empty, and `OwnDen` reports none.
  - Restore: an export restores as a backup does, and its plan names it; the Flatpak refuses one.
  - The commands: `dens den hosting` takes the password to turn on, asks before turning off, and names a held port. M10.3's `dens password` sets one once, then changes it only with the current one; `dens den create` refuses while hosting is off, and its invite makes a second instance the owner.
- Page tests: Hosting's move, from a den to its export, and the removal's refusals; Finish setting up for a den with an owner and one without; a den's row while it's exported.
- The harnesses:
  - The den e2e moves its den: after the member's checks, the host exports it from the command line, and a third container installs this build, restores the export, turns hosting on with `dens den hosting on` and serves it behind Caddy, with the first host's certificate authority. `den.test` then points at the new host, the old one removes its copy, and its owner and the member chat and call through the new host, with the history from before the move.
  - The lifecycle e2e turns hosting on and off with `dens den hosting`, where it used the page's API, on Linux and Windows.
- In the container, both browsers: the browser checks the settings touch.
- The manual test: a den created on Windows, holding tens of gigabytes of files, with a member on another network: backed up with `dens backup` and from the page, then moved from the page to a Debian server in VMware over SSH: restored, hosted from the command line behind Caddy, the router's forwards moved to it, and the copy removed from Windows, which reaches the den as its owner, with a call from outside the network; then M10.3's den started on a fresh server, and its invite redeemed on Windows.

**M10 choices,** picks to confirm before building:

- This is M10, and Android moves to M11–M13, so the table stays in the order things are built.
- No `--headless` install option. A den's export leaves a server's client empty, with nothing to connect to, and M10.3's commands cover what a server needs, so a mode would add a configuration to test for next to no gain: the page is in the binary either way, and its listener is loopback-only, behind a pairing only the desktop user's account can start.
- The export leaves out all of the client, settings included, not only its accounts.
- `dens den export` refuses while hosting is on, where the page's Move turns hosting off after its confirmation.
- Removing a copy needs an export since hosting was last on, and the den answering at its address from another computer: nothing deletes a den that isn't hosted somewhere else.
- Turning hosting back on after an export asks first.
- The names: `dens den export`, `dens den hosting on|off`, `dens den remove`, `dens den create` and `dens password`; on the page, Move the den to another computer and Remove from this computer.
- No option to leave files out of the export. Once the copy the den left is removed, and members' caches go with the new sync epoch, nobody has those files any more, DMs' included; and after M10.1 an export holds up at any size without it.
- M10.1 merges first, and ships with the rest of M10 rather than in a patch release of its own.
- M10.3 can wait, if moving a den is all M10 needs to do now.

**After v1 loose ideas:** onboarding in the page's own first steps, with simple, careful explanations tried on people who haven't seen Dens, bookmarks (per member and per den, so a den's bookmarks always resolve against that den), polls from the composer's + menu, TPM binding for the Windows data key, optional TOTP on the password fallback, simulcast, TURN, end-to-end encrypted calls with SFrame and calls in DMs with them, an optional idle lock, a static dictionary for compressing the den socket's small frames, should measurements show live events matter (built from the protocol's shapes, never members' messages, and named in the upgrade so client and den agree on its version), AVIF: stripped in place by `internal/media`, keeping the original as sent, with dav1d in the module for previews of AVIF images and AV1 videos, and dedup of each member's own channel uploads: their Dens hashes a file once it's stripped, the den keeps the hashes keyed with its data key so its database doesn't show which files it holds, and a file on several messages goes with the last of them.
