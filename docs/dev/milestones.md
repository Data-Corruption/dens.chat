# Dens — Milestones

What each milestone built, the plan for the one under way, and ideas for after it. The design they build toward is [design.md](design.md), with each deployment form's in [installed.md](installed.md), [flatpak.md](flatpak.md) and [android.md](android.md): a section named here, such as Global shortcuts, is one of theirs unless it's one of this file's.

A milestone's plan is written here first, and reviewed before anything is built. Once the milestone is done, what its plan still teaches, such as spike findings and measurements, moves into the design docs' sections, and the rest goes; Git keeps it.

Each milestone ends usable on its own and is tested on Linux and Windows with all four target browsers. All platform-specific code lands in M0, while the seams are still cheap to change; later milestones are shared code, but for M7's keys and the helper's start at login, M9's Flatpak and M10's Android app.

**The Flatpak spike.** Before M9.3, `spikes/flatpak/` answers what the code will lean on, on GNOME 50 and 51 and KDE Plasma 6.4 and 6.5 in VMware, and on SteamOS 3.8 if a Deck or a VM of it is at hand. Its findings come into this document, and it goes when M9.3 lands.

- `dens launch` becoming the service under bubblewrap: how long it lives, a second launch reaching it, two launches at once, and signing out.
- `RequestBackground`: the entry it writes and whether a dialog shows; GNOME's Background Apps listing a service that never had a window, and its close button.
- `RetrieveSecret` across calls and restarts, on gnome-keyring, oo7 and KWallet before and after Frameworks 6.30; a keyring still locked after an automatic sign-in; how long an unlock prompt holds the start.
- The global shortcuts portal from inside the sandbox without `WAYLAND_DISPLAY`, on each desktop, and on Plasma under X11.
- The update monitor: when `UpdateAvailable` fires, `Update` to a build that asks for nothing new, and `Spawn` into it; and whether GNOME Software's automatic updates take Dens's remote.
- The `.flatpakref` link in GNOME Software and Discover, and whether every client checks an Ed25519 key, or the key must be RSA-4096.
- The smallest pinned toolchain that builds the commit, in CI and in a container, with the runtime pinned by its commit; and one real static delta between two stripped builds.

M9.1:

- *The switch.* `types.Configuration.Hosting`, a `*bool`, is nil until something sets it. The first start of a version that has it seeds it from the instance config's `den.enabled`, so a v1.0 install that hosts keeps hosting and every other starts off; from then on the switch alone decides. `den.enabled` stays in `instance.json`, which decodes strictly, and nothing else reads it.
- *Turning it on* takes the local password, as other sensitive actions do, since it opens ports to the internet. The service binds the den listener and the media ports as a start does now, and starts calls, retention and pruning. A port another program holds fails the switch, and the page names the port and the installer flag that moves it (`--den-port`, `--media-udp-port` or `--media-tcp-port`). Home then shows Create your den, as now.
- *Turning it off* asks the owner to confirm that members can't reach the den until it's back on, then stops the den as a service stop does, its listener first, then its sockets, then its calls, and keeps everything it holds. The den's row on home says hosting is off, and leads to the switch.
- *In the service.* Every instance that may host opens the den at start, which costs one row's read while there's no den yet. A hosting runner in `service.Run` serves it while the switch is on, under a context of its own that turning it off cancels; the den's `Start` and `Stop` run its calls, sockets, retention and pruning, which can start again after a stop. With hosting on, a port the service can't bind as it starts leaves the rest serving, so the page can say why, and the runner tries again every 30 seconds. The client router reads the switch where it read `a.Den != nil`, and `dens den owner-invite` refuses while hosting is off.
- *A restore* starts with hosting off, as it starts with no browser paired: hosting is the machine's choice, not the data's, so a copy of a den never goes online by itself.
- *The installer.* `--den` and `--den=false` (`-Den` and `-NoDen`) are refused, with a message that hosting is turned on and off in Dens's settings; the port flags stay. On Windows every install adds the media ports' firewall rules, scoped to `dens.exe` and those ports, which let nothing in while nothing listens; uninstall removes them, as now. The installer no longer checks the den's ports against other programs, which matters only once hosting is on, so `host.PortFree`, which checked the media ports without binding them, goes. `Validate` checks every port of an instance against its others, so an update over a v1.0 instance whose client port is one of its den's says which flag fixes it. The plan the installer prints lists the den's ports as for hosting. A development instance's `--den-port` turns its switch on, as it gave it the den role before.
- *Where it sits.* The settings' System tab gains Hosting: "Host a den on this computer" with the switch, a line on what a den needs, the hosting guide's i and, while hosting is on, the address Caddy forwards to and the media ports. Add a den's dialog ends with a link to it.
- *Calls where the browser can make them.* The page offers calls only where `RTCPeerConnection` exists, and screen share only where `getDisplayMedia` does, and says so where the browser can't. GNOME Web has had no WebRTC since WebKitGTK 2.54, and Android's WebView has no `getDisplayMedia`.
- *Stripped binaries.* Release builds link with `-s -w`, which drops the symbol table and DWARF: about a third smaller (89.4 MB to 56.1 MB for linux-amd64), while panics keep their functions and lines, which live in Go's own line table. Development builds keep both, for debuggers.
- *Formats that move forward.* AGENTS.md's rule for formats before the first release becomes one for after it (see Data across versions), and `migration.go`'s comment goes with it.
- *Docs.* The install guide loses `--den` and `-Den`; the hosting guide starts by turning hosting on, rather than by installing with an option, and the backups guide's move of a den loses the option too. installed.md's instance config and install steps, and lifecycle.md's development instances, follow. M8's finished plan, and the note on the first release, fold into design.md's sections, as M8.2 did with the earlier plans.

M9.2:

- *The form.* `layout.Form` is Installed or Development, and gains Flatpak in M9.3 and Android in M10. `layout.New(app, instance, form)` takes it in place of the development flag, and gives a form it doesn't know no layout; `Layout.Form` replaces `Layout.Dev`, and `Form.Session()` says whether the form runs as its user with no service manager, as only Development does so far. `app.FormOf` chooses it at runtime from the build and, from M9.3, the sandbox.
- *The seams take it* where they took the flag: paths and the permission policy (`layout`, whose `EnsureSession` replaces `EnsureDev`); the data key (`App.loadKey`); lifecycle, where `maintenance.EnsureSessionReady` and `MarkSessionReady` replace the development ones, a session form's service takes its lifecycle lock writable, and `App.prepareSession` writes a session form's own instance config; update checks and their notice, which `App.ChecksForUpdates` keeps to an installed instance with a release host, and which the settings' update options follow; the den's relaxed limits, the debug log level and Pion's log in development; the CLI's check of the service's identity, and its advice when the service isn't running; and a development instance's den port turning its hosting on. Each is a `switch` on the form rather than a type per form: there are few forms, and each differs from the others in a few lines. `dens install` and `dens update` still refuse a development build by the build's own flag, which is about the build, not where it runs.
- *AGENTS.md*'s rule on OS-specific code gains the form: what differs by form is chosen at runtime from `layout.Form`, never by build tags, and like a platform difference never reaches the protocol or the database, and reaches the page only as what it can do.

M9.3:

- *The form.* `/.flatpak-info`, with `FLATPAK_ID` set to `chat.dens.Dens`, makes the Flatpak form, with the paths, permissions and lifecycle [flatpak.md](flatpak.md) describes. Its lifecycle state refuses a version newer than the binary, saying Dens was rolled back and to update it.
- *Unlocking.* Without a remembered copy, the service opens the database, serves the page nothing but its unlock screen, and takes the local password, which opens the key's password copy (Argon2id, as now); then it finishes starting. The unlock screen, and the first local password at pairing, carry Remember on this computer, off by default, and the settings' System tab turns it off again, deleting the copy. This is every Flatpak's start until the member asks it to remember, so it's the path most exercised, not a rare recovery.
- *The remembered copy.* A seam in `host` asks the Secret portal through godbus, reads the secret from the pipe the portal returns, and gives up on a prompt after a timeout. Dens wraps the copy with the portal's secret once two answers match, or with a file's key where they don't or there's no backend, as [flatpak.md](flatpak.md) says. A remembered copy that doesn't open leaves the service locked and is never replaced while it doesn't; once the password unlocks it, Dens remembers anew if the portal answers the same twice. Until the local password exists, at a new instance's first pairing, the key waits in a file wrap, which setting the password removes unless the member asks to remember.
- *Starting it.* `dens launch`, as [flatpak.md](flatpak.md) describes. Once the key is remembered, the settings' System tab shows "Start Dens when you sign in", on, which calls `RequestBackground` as it changes, and gives the autostart line where the portal is missing. The service owns `chat.dens.Dens` on the session bus, for Background Apps' `quit`, and shows how many dens it's connected to through the portal's `SetStatus`.
- *The helper in the service.* `service.Run` starts `shortcuts.Helper` in the Flatpak form, its `Dial` a `net.Pipe` to the hub. `OpenDesktopKeys` tries the portal wherever its interface exists, and skips `Registry.Register` in a sandbox.
- *Updates.* `RunUpdateChecker` stays off in this form. The service watches the update monitor, and the page's notice says an update is available, with Update, or installed, with Restart, which spawns the latest version's `dens service run` through the Flatpak portal and stops.
- *Backups from the page,* in every form: after the local password, a client route streams the archive `dens backup` writes as a download, and the settings' System tab gains Back up. In a session form, `dens restore` runs as its user while the service is stopped: the installed restore's steps without the elevation. In the Flatpak the restored instance starts locked, and opens with the backup's local password.
- *The page* describes only what applies in the Flatpak: hosting needs the installed Dens, voice keys go through the desktop, and updates come from Flatpak.
- *Packaging.* `scripts/flatpak/` holds the manifest, the desktop file and the MetaInfo, with Dens's mark as the icon, and `scripts/flatpak.sh` builds a repository from a release's binaries, for CI and the harness.
- *A harness.* `./scripts/test.sh -flatpak-e2e`: a Debian 13 container builds a repository from this tree's binary, installs the app for a user from it, runs the service as that user, pairs, sets the local password and unlocks a restarted service with it, has it remember with no portals, so in the file wrap, and starts unlocked, joins the den e2e's den, updates to the fixture's next version, and refuses a rolled-back one.

M9.4:

- *The key.* A GPG key with no expiry, since clients can't easily learn a new one: Ed25519, unless the spike finds a client that can't check it. It's made on the owner's machine and kept offline in two places with its revocation certificate, as release.md says. Its secret half is a secret of a GitHub environment, `flatpak`, that deploys only from `main`, so a workflow changed on another branch can't read it.
- *Publishing.* A `flatpak` job runs in that environment once `release` has finished, and `./scripts/ci.sh --flatpak` publishes. It checks the promoted release's cosign signatures and checksums, builds the commit for x86_64 and aarch64 from those binaries, mirrors the live repository down, which checks it against the key, and commits the build on top. It writes the static delta from the last build with `ostree static-delta generate`, since `flatpak build-update-repo` can't raise bsdiff's 128 MB limit on old and new together; then it updates the summary, signs, prunes to the last few builds, and uploads: objects and deltas first, refs and summaries next, deletions last. It learns from the repository which version it holds, so a retry finishes or skips, and its failure leaves the release itself alone. Publications serialize, as releases do.
- *The links.* `flatpak/chat.dens.Dens.flatpakref`, with `GPGKey`, `RuntimeRepo` for Flathub's runtime and `SuggestRemoteName=dens`, and `flatpak/dens.flatpakrepo`, served as `application/vnd.flatpak.ref` and `application/vnd.flatpak.repo`; the repository itself under `flatpak/repo/`. The release host already bypasses Cloudflare's cache, so a summary is never stale.
- *Docs.* The install guide's Flatpak section: the one-click link, `flatpak install`, an alias for the commands (`alias dens='flatpak run --command=dens chat.dens.Dens'`), and that it hosts no den; the privacy guide's row for it; release.md's key, environment, job and recovery; flatpak.md's lifecycle.

**M9 choices,** picks to confirm before building:

- `--den` is refused rather than ignored, so nobody thinks it did something.
- Turning hosting on takes the local password; turning it off, a confirmation.
- The Flatpak's client port is 8494.
- The Flatpak asks for X11, for push to talk on X11 sessions, at the price of a warning as it installs.
- The Flatpak starts at sign-in once its key is remembered, unless the member turns that off; before then a start at sign-in would only wait, locked.
- The lifecycle e2e updates from the real v1.0.0 release.

**After v1 loose ideas:** onboarding in the page's own first steps, with simple, careful explanations tried on people who haven't seen Dens, bookmarks (per member and per den, so a den's bookmarks always resolve against that den), polls from the composer's + menu, TPM binding for the Windows data key, optional TOTP on the password fallback, simulcast, TURN, end-to-end encrypted calls with SFrame and calls in DMs with them, an optional idle lock, a static dictionary for compressing the den socket's small frames, should measurements show live events matter (built from the protocol's shapes, never members' messages, and named in the upgrade so client and den agree on its version), AVIF: stripped in place by `internal/media`, keeping the original as sent, with dav1d in the module for previews of AVIF images and AV1 videos, and dedup of each member's own channel uploads: their Dens hashes a file once it's stripped, the den keeps the hashes keyed with its data key so its database doesn't show which files it holds, and a file on several messages goes with the last of them.
